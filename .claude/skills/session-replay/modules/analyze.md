# session-replay · analyze 模式

对已有的 `projects/replay/<导出目录>/` 产物做问题分析，产出**可执行的优化方案**。

核心原则：**不要通读 `replay.md`**（动辄 50 万字符）。按三层漏斗收敛——先算指标定位可疑区间，再归因，最后只对高优先级项回时间线取证。

## 第 1 层 · 确定性指标（脚本算，零 token）

```bash
python .claude/skills/session-replay/scripts/replay-analyze.py [<replay目录或replay.json>]
```

留空取 `projects/replay/` 下最新一次导出。报告会打印到 stdout，**同时自动留档到 `<回放目录>/metrics.md`**。常用参数：

- `--format json` 需要程序化后处理时用（留档为 `metrics.json`）
- `--out <path>` 指定留档位置
- `--no-save` 只打印不落盘
- `--repeat-threshold N` 重复命令阈值（默认 2）
- `--rework-threshold N` 文件返工阈值（默认 3）

事件明细（取证辅助，与 metrics 同级留档）：

```bash
python .claude/skills/session-replay/scripts/session-timeline.py [<replay目录或replay.json>]
```

留档为 `<回放目录>/timeline.md`（完整工具调用序列表：时间/域/工具/对象/结果，按时间升序）。
对象列对 Task / MCP·TFS / CodeGraph 做语义化描述；回放数据中 TFS 工作项标题乱码时，可先经
TFS MCP 现查后用 `--tfs-titles '{"<工作项ID>": "<标题>"}'` 补注。

脚本输出七节，各自指向一类问题：

| 节 | 指向的问题 |
|---|---|
| 时长分解 | 墙钟 vs 真实执行：等待型工具（AskUserQuestion/TaskOutput）单列，事件间 gap 超阈值（默认 60s）归人工闲置——回答「时长里多少是真干活」 |
| 重复命令 | 轮询式推进（同一命令反复调）、试错式调参（同一命令改参数重试） |
| 失败聚类 | 同签名错误聚成一条，次数越高越是系统性缺陷而非偶发 |
| 子代理健康度 | `空转` = 派发了没干活；`高失败率` = 契约缺失；`耗时离群` = 阻塞或死循环 |
| 文件返工 | 同一文件反复写 = 需求理解不到位或校验滞后 |
| 用户输入 | 第一条是初始诉求（用于判断意图偏移）；中途插话是 agent 跑偏/卡住的强信号，优先看 |
| 工具分布 | 对照任务性质判断工具选型是否合理 |

## 第 2 层 · 归因分类（LLM 判断）

把第 1 层暴露的每个可疑点归到下表**恰好一类**——因为修复位置完全不同。归错类会导致修了没用。

| 类别 | 识别特征 | 修复位置 |
|---|---|---|
| 契约缺失 | agent 在几种参数组合间盲试后成功；错误信息是"参数不匹配/未知字段/schema invalid" | 对应工具接口定义、技能说明、agent 定义 `.claude/agents/*.md`、脚本参数校验与错误提示 |
| 外部不稳定 | `socket hang up`、`xxx is not iterable`、`Cannot read properties of null` | 重试策略 + 入参规范化；必要时给外部服务提缺陷 |
| 流程设计缺陷 | 同一命令高频重复但每次都成功；状态机每推进一步就要往返一次 | 对应流程脚本的批量处理、检查点与恢复机制 |
| 一次性失误 | 只出现 1 次、无模式、成本低 | **不修**，明确写进"已忽略" |

判断依据必须落到证据（时间戳 / 工具名 / 错误签名），禁止用"感觉绕路了"这类印象。

重复调用不能仅凭命令相同直接归为流程空转。只有同一命令发生在同一执行阶段，且输入不变、输出不变、任务状态没有推进时，才能归因为空转；同一命令在不同阶段成功推进任务状态属于有效的流程执行，不是重复劳动。

同时检查两个脚本算不出来的维度：

- **意图偏移**：对比"初始诉求"与最终改动文件、最后一次 assistant 输出，是否跑题
- **可沉淀经验**：是否有值得保留的用户纠正或确认，将其依据和改进建议记录在当前回放目录的 `review.md`。

## 第 3 层 · 取证（只对 P0/P1）

对定级为 P0/P1 的项，回 `replay.md` 读对应时间戳附近的时间线，确认根因不是猜的。P2/P3 不取证，避免浪费。

在 `replay.md` 里用时间戳定位，例如：

```bash
grep -n "2026-07-30 14:1" projects/replay/<dir>/replay.md | head
```

## 定级规则

| 级别 | 判据 |
|---|---|
| P0 | 系统性缺陷 + 每次都复现 + 有明确修复落点（契约/agent 定义） |
| P1 | 系统性缺陷但成本中等，或修复落点需要改脚本逻辑 |
| P2 | 效率问题，不影响正确性（轮询、往返） |
| P3 | 工具/流程本身的增强，非本次会话特有 |

排序按 ROI，不按发现顺序。

## 第 4 层 · 出报告

分析结论必须落盘，不能只停留在对话里——下次会话看不到聊天记录，但能读到文件。

写入 `<回放目录>/review.md`，与 `metrics.md`（第 1 层指标）、`timeline.md`（事件序列表）、`replay.md`（原始证据）同目录，构成完整证据链。用 Write 工具直接写，模板：

```markdown
---
title: 会话复盘 · <session前8位>
contract: SessionReplay
version: 1.0.0
status: active
created_at: <YYYY-MM-DD>
updated_at: <YYYY-MM-DD>
owner: winning\li_lei
---

# 会话复盘 · <session-id>

| 项 | 值 |
| --- | --- |
| 回放目录 | `projects/replay/<dir>/` |
| 初始诉求 | `<first_prompt>` |
| 时长 / 轮次 / 调用 | <从 metrics.md 概览抄> |
| 真实耗时 | <机器执行 + 模型思考 + 子代理 effort 合计（AI 团队总投入口径），数值取自 metrics.md 时长分解> |

## 结论

<1-2 句：这次会话做了什么、结果是否正确、有无意图偏移>

| # | 现象 | 归因 | 证据 |
|---|---|---|---|

| 优先级 | 动作 | 落点 | 预期 |

```

写完后**对话里只给浓缩版**：结论 1-2 句 + 问题清单 + 方案表 + 建议先做哪项，末尾报告 `review.md` 路径。不要在对话里重复 `metrics.md` 的原始数据。

## 边界

- 只读 `replay.json` / `replay.md`
- 只向**回放目录**写 `metrics.md` / `timeline.md` / `review.md`
- 不自动执行任何优化动作
