# Frontend Feedback Signals（前端反馈信号清单）

> **本文件为前端反馈信号细则的唯一权威**（04 §5.4 的操作化；总原则引自 04 §5.2）。语义背景：04（根级现行版 `projects/multica/04-engineer-development-design.md`）。

## 总原则（04 §5.2 引述）

> 主要代码修改之前必须识别能证明本次行为或修复正在收敛的可靠、可观察 Signal，并在修改过程中持续使用。

Signal 不必是同一个测试框架；编译成功不能替代已要求的行为验证或 Task Verification；无法自动测试时不得伪造 RED / GREEN。

改动分类与必做检查类型见 [local-validation.md 的验证深度分级](local-validation.md#验证深度分级2026-11-03-增补)，具体 Signal 按本文件选择。该文件的浏览器命令映射用于需要运行时观察的检查，不表示所有行为逻辑变更都必须启动浏览器。

## 可用 Signal（按改动类型选最小可靠集）

| 改动类型 | 首选 Signal | 备选 / 补充 |
|---|---|---|
| 业务逻辑 / 纯函数 | Unit Test（若仓内有测试框架） | 浏览器控制台可复现验证记录 |
| 组件状态 / 交互约束 | Component Test（若有框架） | 浏览器行为观察（操作步骤 + 截图） |
| 路由 / 表单 / 错误提示 / 权限可见性 | 能覆盖受影响行为的现有测试 | 未覆盖风险所需的浏览器行为观察；必要时 E2E |
| 纯展示 / 隐藏 | 按 local-validation.md 的验证深度分级执行 | 页面人工核查建议 |
| 样式 / 布局 | 代码核对；无法据此判断的视觉变化使用浏览器观察 + 截图对比 | — |
| 构建 / 依赖 / 配置 | Build（`vue-cli-service build`） | Lint |
| 纯重构（无行为变化） | Build + Lint PASS + 受影响代码核对及适用的既有测试 | 未覆盖风险所需的关键路径浏览器抽查 |

## 目标仓测试能力核实

- 测试能力以目标仓当前的依赖、测试配置和可执行命令为准；本 Skill 的概述或历史命令映射中的“无框架 / 无运行器”不替代本次核实。有可用测试时优先复用，不虚构命令；没有测试框架本身不构成必须执行 E2E 的理由。
- 浏览器观察须可复现：写明操作步骤、URL / 路由、观察点，附截图或操作记录引用；
- 构建与 Lint 结果如实记录，不冒充实际交互或真实后端链路的执行证据。

## 选择纪律

1. **最小可靠**：覆盖当前 `task_refs` 的改动面即可；
2. **按风险补充行为证据**：用户可观察的变化不自动要求浏览器验证；仅当现有测试与代码核对不能充分证明受影响行为时，补充针对性的浏览器验证。浏览器验证不自动扩大为真实后端或完整业务链路验证；用户明确要求或已批准 Contract 中的必做项仍须执行，调整按现有变更流程处理；
3. **Corrective 回归**：可稳定复现的缺陷须留修复前 FAIL / 修复后 PASS 的对应证据（修复前截图/报错记录 vs 修复后）；不可复现时用可靠替代证据并写明局限（04 §5.6）；
4. 跨仓 Contract（如依赖后端接口变化）保留约束引用，必要时报 Delivery Lead 追加组合 Verification Task。
