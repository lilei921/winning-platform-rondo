为 [Multica 研发任务闭环方案 v1.3.5](../../archive/multica-squad-centric-delivery-v1.3.5.md) §5 TFS Sync、§6 Delivery Issue 启动和 §7 Analysis 验证 TFS Context 的获取方式。

## 3. 调用方式与需求详情

固定 provider：`winning-tfs-2018-mcp`。以下是工具调用及其 JSON 参数，不是 Shell 命令：

| 工具 | 参数 | 作用 |
| --- | --- | --- |
| `tfs_get_work_item` | `{"id":221943}` | 获取需求详情 |
| `tfs_list_attachments` | `{"id":221943}` | 独立获取附件列表 |
| `tfs_get_work_item` | `{"id":252984}` | 获取对照需求详情 |
| `tfs_list_attachments` | `{"id":252984}` | 验证无附件的成功返回 |

本运行时对应的完整工具名为 `mcp__winning_tfs_2018_mcp__tfs_get_work_item` 和 `mcp__winning_tfs_2018_mcp__tfs_list_attachments`。本次两个接口都只传入 `id`；跨 Collection 的路由能力没有验证。

工具成功响应的 `content` 文本块包含 JSON 字符串：详情解析为对象，附件列表解析为数组。应先检查工具错误，再解析 JSON 和校验结构，不能将错误消息当作需求内容。

| 字段 | 返回值 |

| `title` | 公版研发_DF6.0_数据集成调度最小量部署及最小量质控 |

`project` 与 `productName` 是不同事实，不应因产品名含“数据采集”而改写其所属 TFS 项目。`changedDate` 是工作项变更时间，不是本次查询时间。

## 4. 附件验证

### 4.1 详情中没有附件列表，不等于没有附件

本次 `tfs_get_work_item` payload 未返回附件列表，单靠详情无法判断是否存在附件。必须调用 `tfs_list_attachments`。

221943 的附件接口原始返回是含 3 个对象的数组，每项只有 `id`、`name`、`url`、`comment`。保存文件外围的 `workItemId`、`source`、`attachmentCount`、`attachments` 是本地封装，其中数量通过数组长度计算。

| 返回 `id` | 返回 `name` | URL 中的附件标识 | `comment` |
| --- | --- | --- | --- |
| 0 | attachment-0 | 952bac46-c197-47c9-a875-cd37c2a71093 | 空 |
| 1 | attachment-1 | 02924779-fcc4-4bf3-af5b-02590160dc9b | 空 |
| 2 | attachment-2 | 71af92b8-1ad5-4610-979c-fffe673ca822 | 空 |

完整 URL 见 [221943.attachments.json](221943.attachments.json)，形式为 `http://tfs2018-web.winning.com.cn:8080/tfs/WN_Data_Platform/_apis/wit/attachments/<标识>`。

不能将 `id=0/1/2` 当成已验证的 TFS 稳定附件标识；优先保留完整 URL 作为定位证据。`attachment-*` 不包含真实文件名、扩展名、大小或媒体类型。正文虽然提到 Excel 和 UED，但本次无法把三个附件逐一对应到这些用途。

### 4.2 附件状态必须区分

| 情况 | 可作出的判断 |
| --- | --- |
| 成功返回非空数组 | 有附件；内容是否已获取另行记录 |
| 成功返回 `[]` | 该次查询返回无附件，252984 覆盖此情况 |
| 未调用、工具报错、超时或结构异常 | 附件情况未知，不能记为 0 |

221943 正文依赖附件说明，因此在附件内容尚未获取前，不能宣称已收集完整分析输入。下载权限、真实文件名解析和二进制完整性均为后续验证项。

## 5. 乱码定位与修复

### 5.1 已确认的事实

221943 本地文件可按 UTF-8 解码并解析 JSON，但包含两处乱码，每处有 3 个 Unicode 替换字符 `U+FFFD`，合计 6 个：

| 字段路径 | 原始片段 | 本地修复后 |
| --- | --- | --- |
| `requirementAnalysis` | `背景描述[概述背景及需要解决的���题或目的]` | `背景描述[概述背景及需要解决的问题或目的]` |
| `fields["Winning.Demand.Analysis"]` | 同上，位于 HTML 模板内 | 同上，保留原 HTML |

再次调用 `tfs_get_work_item({"id":221943})`，返回的两个字段仍包含相同乱码。这证明乱码在 MCP 返回时已经存在，并非这次 JSON 写盘引入。**尚未检查 TFS HTTP 原始响应或 MCP 实现，不能进一步断言是 TFS 存储损坏，还是工具读取、解码环节造成。**

252984 的相同分析模板为“需要解决的问题或目的”，提供了本次局部修正的参照。修复是基于模板的文本推定，不是从 TFS 恢复出了原始字符；不能把此做法推广为任意业务文本的自动猜字。

### 5.2 实际处理

1. 保留重新查询的 payload 为 `221943.raw.json`。
2. 仅在 `221943.json` 的上述两个字段中将 `���题` 替换为“问题”。
3. 重新解析 JSON，确认修复版本 U+FFFD 数量为 0。
4. 按对象比较原始与修复版本，确认除两处指定值外没有数据变化；缩进、字符转义等序列化差异不算业务数据修改。

没有修改 TFS。原始文件继续含有乱码是有意保留证据。将其重新保存为 UTF-8 或增加 BOM 不能恢复已经变成 U+FFFD 的内容。

整理本文时还观察到另一类问题：Python 默认使用 GBK 向终端输出 U+FFFD 时触发 `UnicodeEncodeError`。显式设置标准输出为 UTF-8 后可正常读取展示。这属于终端输出编码问题，与 payload 自带替换字符是两个独立问题；排查时应分别验证文件字节、解析后的字符和终端编码。

## 6. 对 v1.3.5 获取需求详情的接入建议

以下为基于本次样本的实现建议，尚未实现或验收生产同步器。

### 6.1 采集与校验顺序

1. 调用详情接口，校验工具成功、JSON 对象结构和返回 `id` 与请求一致。
2. 调用附件接口，校验成功状态和数组结构；与详情请求分别记录结果。
3. 在任何清洗前保存两个接口的原始 payload，同时记录工具名、请求参数、采集时间；后续可增加文件摘要用于复核。
4. 校验必需字段和文本质量，扫描 U+FFFD；对 HTML 保留原文，按展示需要另行生成可读文本，保留链接、段落和正文引用。
5. 将清洗值、修正理由、原始值及原始证据分开保存。未知业务文本不自动猜字，交 Workitem Analyst 核实。
6. 对正文依赖的附件获取内容并记录结果；无法读取时显式列入缺失输入。
7. 将校验后的 TFS Context 提供给同步和分析环节，避免以“JSON 可解析”替代“输入完整”。

两次请求不是原子快照；本文未证明详情和附件来自同一修订时刻，也未验证只依赖 `changedDate` 就能覆盖所有附件变化。

### 6.2 与方案字段及职责对应

| v1.3.5 使用位置 | 数据来源与处理 |
| --- | --- |
| §5 `source` | 同步器设置为 `tfs` |
| §5 `tfs.id` | 由返回 `id` 转为方案示例使用的字符串，并核对请求 ID |
| §5 `tfs.type` | 源值为“需求”；若内部使用 `Requirement`，显式映射并保留原值 |
| §5 `tfs.url` | 保存详情返回的 `url` |
| §5 `tfs.changed_at` | 使用 `changedDate`，另行记录采集时间 |
| §5 TFS 原始上下文 | 基本信息、HTML 描述、分析原文、`fields`、独立附件列表及查询结果 |
| §6–§7 TFS Context / Context Pack | 在原始证据基础上提供可读内容、附件内容、修正记录与缺失输入 |
| §8 Analysis Gate | 取数成功只提供上下文证据；分析模板、验收标准、附件缺失仍需按 Route 检查 |

TFS 的 `state=活动`、`assignedTo=李磊` 是外部管理事实，不直接覆盖 Multica 的执行状态或负责人。按 §5，新建 Delivery Issue 仍分配给 Delivery Squad 并保持 backlog；已有 Issue 只更新 TFS 管理字段，不主动启动研发。本次未验证这些写入行为。

## 7. 已完成校验与后续验证范围

已通过的本地证据校验：

- 五份 JSON 均能以 UTF-8 解析；工作项 ID 与文件用途一致。
- 221943 原始和修复版本均保留 60 个 `fields` 字段。
- 原始版本含 6 个 U+FFFD；修复版本为 0；对象差异仅为两处指定模板修正。
- 附件封装数量与数组长度一致：221943 为 3，252984 为 0。
- 252984 详情未检出 U+FFFD；这不等于完成了对所有潜在乱码类型的检测。

后续需要单独验证：

- 三个附件的下载、真实文件名、文件格式、可读性，以及与正文所述材料的对应关系。
- 乱码产生于 TFS 存储还是 MCP 解码的准确位置；异常重试与人工核实策略。
- 不存在的 ID、无权限、网络错误、附件查询失败等异常分支。
- 增量采集和附件变更检测，以及 Multica 创建、更新幂等、字段归属和状态保护。

因此本次结论是：**需求详情与附件目录取数可行，源文本质量需要额外校验；完整附件上下文与 Multica 端到端接入尚待验证。**
